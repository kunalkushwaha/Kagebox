Give the agent a desk, not your keys.

An autonomous agent can open a shell, install packages, edit files and drive a browser for an hour without asking. That is what makes it useful, and what makes running one on your laptop a strange decision. Kagebox gives it a whole machine to work on — and possibly wreck — that simply isn’t yours.

Quickstart What it does and doesn’t protect Source

01The premise

You would not give a new hire root on the machine holding your SSH keys.

Most of the safety conversation is about making the agent trustworthy. But you cannot prompt your way to safety when the thing on the other end has a shell. If it can run curl, it can exfiltrate. If it can run rm, it can delete. No amount of “please be careful” changes the blast radius.

The more useful question is the one we already answered for humans and for services decades ago: what can this thing reach if it turns on me? We don’t make employees incapable of harm — we contain them. A workstation, not the CTO’s laptop. Scoped credentials, not the master key. And an audit trail.

The design, in one sentence

Give the agent a full machine that isn’t yours; let it reach models and the web through a single door you control; and keep every credential, and the final say, on your side of it.

02How the boundary is built

Four controls, each placed where the agent can’t reach it.

HOST (you) │ SANDBOX (agent, root in here) │ API keys, Claude auth ──┐ │ ▼ │ ollama ◀────────── bridge gateway ◀──┼──── model calls (no key ever crosses) │ allowlist │ │ audit log │ ▼ │ nftables egress ◀──────────────────┼──── everything else (keyed to the VM interface) │ ▲ │ └─ guest root cannot alter this workspace/ ◀───── shared folder ──────┼───▶ ~/workspace

Its own kernel, not yours

The agent runs in a KVM microVM, not a container. A container shares your kernel and a container escape is a regularly-discovered class of bug; a microVM makes the boundary a hypervisor. The agent gets a whole Linux box — it just can’t see your filesystem, processes, or network.

The keys never cross the desk

Model calls route through a broker running as you, on the host, which injects the credential into each request. From inside, the agent talks to a plain endpoint and never holds a secret — and any credential header it sends is dropped, not relayed, so it can’t smuggle its own key to an upstream either.

A door that locks from the outside

An earlier version enforced egress inside the VM, which is theatre: the agent has root there and can flush its own firewall away. The rule now lives on the host, on the interface the VM sits behind. The agent can be compromised to root and still can’t open it.

The boundary has to prove itself

Every control here fails open — a rule that silently didn’t load looks exactly like one that’s working. So ./kagebox verify climbs inside the running VM and tries to break out, and an adversarial suite attacks each stated invariant on every push.

03Quickstart

Linux host with KVM, multipass, and Ollama for local models.

# check the host, then build the sandbox (~10 min)
git clone https://github.com/kunalkushwaha/Kagebox.git && cd Kagebox
./kagebox doctor
./kagebox setup

# work in it
./kagebox shell            # then: hermes
./kagebox verify           # assert the boundary from inside

Use a cloud brain for heavy reasoning — the key stays host-side:

cp bridge/secrets.env.example bridge/secrets.env
echo 'GEMINI_API_KEY=...' >> bridge/secrets.env
./kagebox bridge restart && ./kagebox backend gemini

04Network policy

Egress runs under a named profile you choose.

ProfileReachesFor
sealedthe model bridge, nothing elseuntrusted input; task mode forces it
research (default)search, Wikipedia, arxiv, Crossref, HNreading and writing
devresearch + PyPI, npm, crates, Go, GitHubcoding agents
openeverythingyou’ve decided
 
./kagebox egress profile           # list them
./kagebox egress profile dev       # switch, and re-apply

Your own vm/egress-allowlist.txt is layered on top of whichever profile is active — a profile is a floor, never a ceiling.

Why the default isn’t the tightest one

A sealed default that blocks every real task teaches people to run egress off once and never turn it back on — strictly worse than a curated allowlist. That is a usability judgement with a security cost, and it is worth stating plainly: no profile except sealed is exfiltration-proof. An allowlisted search endpoint is a data channel — a query string can carry a key out, slowly — and CDN-fronted names drag their neighbours along. Profiles bound the blast radius; they don’t make the agent safe to point at hostile input.

When an allowlist can’t express what you need

Following a search result to an arbitrary domain is exactly what an IP allowlist cannot cover. Two bounded escapes exist, and both close again:

  • ./kagebox research "…" — opens egress for one run at the keyboard, re-seals after, even on Ctrl-C.
  • The warden — the sandbox requests named destinations, you approve from your phone, and the grant carries a kernel-side timeout so it expires even if the warden is killed. The guest can ask; only you can grant.

06What it does not protect

Naming the gaps is part of the design, not an embarrassment to bury.

  • DNS still resolves. A determined process can whisper data out one lookup at a time. Low bandwidth, but enough for a key.
  • CDN fronting. An allowlisted name shares front-end addresses with unrelated sites, so allowlisting one permits others. Port-scoping doesn’t help — the neighbours are on :443 too.
  • The shared folder is a two-way door, and you are the transport. Agent-authored files can carry code that runs on the host the moment you act on them.
  • Hypervisor 0-days. VM isolation is strong, not absolute.

The full accounting is in the threat model.
